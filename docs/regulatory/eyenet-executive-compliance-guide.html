What EyeNet is from a compliance point of view

EyeNet is an on-premises computer-vision and operations platform. A local installation processes camera, presence, and automation events at the customer site. Authority (licence / identity) and Headscale (Matrix VPN mesh) sit on the internet only as coordination services. After first enrollment, leaf devices prefer LAN, then fall back to the private mesh (100.64.x.x). There is no requirement to send video to a public cloud.

That architecture is a strong privacy-by-design baseline. It is not a certificate. Legal risk still depends on which module is switched on, what it infers, and where it is used.

  • NIS2 registration if the customer is an essential / important entity (Greece Law 5160/2024; France transposition pending as of this date)

Executive summary — readiness under strict frameworks

EyeNet is engineered so a customer can operate under strict EU regulatory frameworks (GDPR, national DPA doctrine, and where applicable NIS2 / national cyber requirements) without shipping video to a public cloud. Technical competence here means the platform can implement privacy-by-design and Art. 32-class controls by default, expose auditable decisions, and keep high-risk capabilities off until the customer’s DPO / legal process authorises them.

Verdict for leadership: EyeNet is operationally ready as a privacy-first on-prem processor stack. Lawfulness, DPIA, notices, and NIS2 entity registration remain the controller’s duty — typically led by the customer’s DPO with EyeNet / distributor technical evidence.

Authority, fine-grained keys, and bootstrap

Authority is the licence and hierarchy control plane. Local Node remains the account and RBAC system. Bootstrap no longer invents a second local licence secret.

6.1 Credentials

Credential Shape / issuer Used for Must not be used for
Software licence = application_key lic_ + 32 hex, Authority Activate, report state, update, platform VPN enroll Sharing across sites; live secret in QR
Bootstrap-admin (temporary) admin@authority.local when flag enabled First privileged Authority setup Production — disable after setup
Local user JWT Node Day-to-day API via roles + capabilities Licence activation
VPN auth_key Headscale pre-auth via Authority One-time mesh join API calls
Device api_token HMAC(secret, installation_uuid) Discovery / resolve-platform Owner login
Invitation token Authority User-first onboarding of roles Device enroll
Fine-grained means: one machine licence key per installation, capability-level local permissions, and separate mesh/device tokens. There is no shared god-key that both unlocks video and enrolls phones.

6.2 Local installation bootstrap (target path)

  1. Start local backend services; frontend bootstrap collects platform connection if missing.
  2. Persist application_key + durable installation_uuid. Saving settings is not activation.
  3. First owner registers with the approved owner email.
  4. Node calls Authority POST /api/v1/installations/activate with key + email + UUID.
  5. Only after approved=true does Node grant local owner, admin, user.
  6. Authority remains source of truth for licence status, warning / offline grace; Node can enter safeguard.
  7. Disable Authority bootstrap-admin.

Mismatch of email, unknown key, or reuse of the same key on a second UUID is rejected.

Matrix VPN mesh (platform + mobile APKs)

The Matrix is the commercial overlay on a Headscale / WireGuard mesh. Each app is its own VPN node. Platforms do not share a database. Authority stores the only shared link: which client is assigned to which platform.

How a device finds home

Enrollment (one internet round-trip) returns:

  • platform_tailscale_ip — stable mesh IP
  • platform_local_ip — current LAN IP
  • platform_hostname, matrix_group_id, auth_key, api_token

Steady-state host order:

  1. platform_local_ip (LAN)
  2. manual backendIP
  3. vpn_platform_tailscale_ip (remote)

Tags

  • tag:install-<hex> — immutable installation identity
  • tag:platform / tag:client / tag:analytics — role (exclusive)
  • tag:camera / tag:signage / future tag:presence — type
  • tag:matrix-<uuid> — mesh membership

ACLs should keep clients hub-and-spoke to their assigned platform. Cross-tenant mesh paths are a defect.

7.3 Mesh / mobile APK compliance

Control Why EyeNet Gap

Open product / ops items that affect the claim

Engineering or deployment facts, not legal theory:

  1. Rebuild mobile camera / player APKs with LAN-first platformHost and publish real mesh IPs.
  2. Deploy Node report_platform_local_ip so tokens stop returning platform_local_ip: null.
  3. Enroll the on-prem box as tag:platform — never the Hetzner Authority node.
  4. Turn off AUTHORITY_BOOTSTRAP_ADMIN_ENABLED after first setup.
  5. Do not put application_key in QR payloads as a live secret.
  6. Add an operational “legal basis / DPIA ID” field to trigger and Presence policy records.
  7. Publish a DSAR / erasure runbook for VMeta individuals, Presence sessions, and trigger logs.
  8. Keep webhook and communications actions on an allowlist with payload minimisation.
Until items 1–3 are done, treat remote APK access as not production-ready from a security-evidence standpoint.

Appendix C — Jurisdiction & use-case law summary

Condensed English rendering of the March 2026 EyeNet jurisdiction map (Greece · EU · USA). Informational only — not legal advice. Source document path in repo: docs/product/legal/Συνοπτική_Νομοθεσία_Προσωπικών_Δεδομένων_Ελλάδα_ΕΕ_ΗΠΑ.md.

EyeNet’s on-prem / offline / modular design is a strong compliance baseline, but obligations still differ by jurisdiction and by which function is enabled. High-risk functions: identification, demographic profiling, cross-camera tracking, third-party webhooks, multi-tenant logs.

C.1 Short frame by geography

Geography Core frame What matters for EyeNet
Greece GDPR + Ν. 4624/2019 · Authority: ΑΠΔΠΧ (HDPA) Workplace image processing, video surveillance, biometrics / sensitive data, proportionality and minimisation
European Union GDPR principles (lawfulness, transparency, purpose, minimisation, accuracy, storage limitation, security, accountability) DPIA for video analytics; clear legal basis; security measures; retention; data-subject rights; biometrics = special category (Art. 9)
United States No federal GDPR equivalent — fragmented state / sectoral law (e.g. CPRA, BIPA) Notice / opt-out gaps; biometric consent where required; security failures → litigation risk

C.2 Common requirements (all markets)

  • Privacy by Design / Privacy by Default
  • Purpose and data limitation (only what is necessary)
  • Retention policy with clear time limits
  • Technical measures: encryption, role-based access, audit logs
  • Process for data-subject rights (access, erasure, objection where applicable)

Underage detector (POS) Positive when age-threshold only, no identification / image retention Generally acceptable with notice; watch biometric statutes Age estimation only; minimal logs; auto-delete frames
Security officer / wearable / mobile camera High risk in public / mixed spaces; extensive DPIA; geo/time limits State-variable; transparency and access control critical Explicit start/stop; short bursts; no standing stream

C.4 Critical differences (executive takeaway)

  1. EU / Greece: stricter, principle-driven frame (lawfulness, proportionality, documentation, DPIA).
  2. USA: decentralised / state model with elevated practical risk on biometrics and class actions.
  3. For EyeNet: security and compliance use cases are strong commercially, but demographic analysis, employee monitoring, and wearable continuous capture need the most legal discipline.

C.5 Minimum commercial compliance plan

  • Jurisdiction matrix (Greece, rest of EU, US states as needed)
  • DPIA templates per use case (Signage, Gate, Underage, Wearable / Presence camera)
  • Feature flags per country / state
  • Retention standards (metadata-only where feasible)
  • Legal / technical review before each sensitive-sector pilot
Go-live gate: jurisdiction check · DPIA where required · notices · retention / access / crypto / logs · named compliance owner · quarterly review. Full pilot checklists live in the March 2026 legal summary (§7–§11).
