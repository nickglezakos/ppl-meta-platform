# Release Notes: v2.19.85 - Super-Individual Hierarchy Fetching

**Release Date**: January 2025  
**Type**: Feature Enhancement + Bug Fix  
**Priority**: High  
**Status**: ✅ Implemented

---

## Overview

This release resolves a critical issue where super-individuals (result of hierarchical MVR merging) were only displaying their own direct individual appearances instead of showing ALL appearances from the entire merged hierarchy. This was causing users to see only 5 appearances instead of 45+ from merged super-individuals.

---

## Problem Statement

### Issue
When Collections screen passed a super-individual UUID to PersonObjectsDetailScreen after hierarchical merge:
- Screen treated super-individual as a regular MVR person
- Called `getMVRPersonAnalysis()` which only returns direct individuals
- **NEVER called** the hierarchy endpoint to get merged MVR people
- Result: Only showed 5 appearances instead of 45+ from all merged MVR people

### User Impact
- Users expected: "I am expecting to see all the appearances by all the member individuals that are at least 15 MVR people and at least 45 person objects"
- Users saw: Only 5 appearances from super-individual's direct individuals
- Missing: ~40 additional appearances from 14 other merged MVR people

---

## Solution Implemented

### 1. Enhanced PersonObjectsDetailScreen (person_objects_detail_screen.dart)

#### Added Hierarchy Detection & Fetching
**Location**: Lines 1520-1570 in `_loadCrossVideoData()` method

**New Logic Flow**:
```dart
if (loadingMVRPeople && hierarchicalMergeApplied) {
  // For each super-individual UUID
  for (final superIndividualUuid in context.individualUuids) {
    // 1. Fetch hierarchy
    final hierarchyResponse = await apiClient.get(
      '/api/v1/mvr-people/super-individual/$superIndividualUuid/hierarchy',
    );
    
    // 2. Check if merged or standalone
    final isSuperIndividual = (hierarchyData['merged_mvr_people'] as List).isNotEmpty;
    
    // 3. Build analysis from full hierarchy
    final analysis = AggregatedIndividualAnalysis.fromSuperIndividual(
      superIndividualUuid: superIndividualUuid,
      hierarchyData: hierarchyData,
      sessionUuid: context.sessionUuid,
      startTime: startTime,
      endTime: endTime,
    );
    
    // 4. Fallback to direct MVR if hierarchy fails
    // ...fallback logic...
  }
}
```

**Key Features**:
- ✅ Detects when hierarchical merge was applied
- ✅ Calls hierarchy endpoint for each super-individual
- ✅ Parses complete hierarchy (super-individual + merged MVR + all individuals)
- ✅ Fallback to direct MVR loading if hierarchy fails
- ✅ Filters individuals by date range (startTime/endTime)
- ✅ Aggregates all appearances from entire hierarchy

#### Added Helper Method
**Location**: Lines 1792-1890 in `_loadSingleMVRPerson()` method

**Purpose**: Fallback method to load a single MVR person's data when:
- Hierarchy endpoint fails
- MVR is not a super-individual (standalone)
- Error occurs during hierarchy fetching

**Benefits**:
- Code reusability (used in both hierarchical and direct loading paths)
- Consistent error handling
- Prevents code duplication

### 2. Enhanced AggregatedIndividualAnalysis Model (cross_video_analysis_models.dart)

#### Updated fromSuperIndividual Factory Constructor
**Location**: Lines 214-315

**Previous Signature**:
```dart
factory AggregatedIndividualAnalysis.fromSuperIndividual(Map<String, dynamic> json)
```

**New Signature**:
```dart
factory AggregatedIndividualAnalysis.fromSuperIndividual({
  required String superIndividualUuid,
  required Map<String, dynamic> hierarchyData,
  required String sessionUuid,
  DateTime? startTime,
  DateTime? endTime,
})
```

**Enhancements**:
1. **Date Range Filtering**:
   - Filters individuals by `first_seen_timestamp` and `last_seen_timestamp`
   - Applies startTime/endTime constraints from search parameters
   - Only includes relevant appearances

2. **Complete Hierarchy Parsing**:
   - Extracts super_individual data
   - Parses merged_mvr_people list
   - Converts all_individuals to IndividualAppearance objects
   - Calculates unique video count from all individuals

3. **Accurate Metrics**:
   - `totalAppearances`: Count of filtered individuals
   - `uniqueVideos`: Unique video UUIDs from all individuals
   - `firstSeen`: Earliest timestamp from all individuals
   - `lastSeen`: Latest timestamp from all individuals
   - `personObjectUuids`: All individual UUIDs

4. **Hierarchical Fields**:
   - `isSuperIndividual`: True if merged_mvr_people is not empty
   - `mergedMVRCount`: Total MVR count from hierarchy
   - `mergedMVRPeople`: List of MergedMVRPerson objects
   - `bestFaceThumbnail`: Featured person object UUID

## Lazy Loading Implementation

### Routes Data
**Current Behavior**: Routes are already lazy-loaded via caching mechanism
- Routes data is NOT loaded on initial screen render
- Routes are only fetched when user switches to "Routes" tab
- `_cachedRoutesData` caches routes to prevent repeated API calls
- `_isLoadingRoutes` flag prevents concurrent requests

**Benefits**:
- ✅ Initial screen load is not blocked by routes data
- ✅ Routes only load on-demand when needed
- ✅ Cached data reused across tab switches
- ✅ Prevents unnecessary API calls

**Future Enhancement** (if needed):
- Could add per-individual route loading (load routes for one individual at a time when expanded)
- Current implementation is sufficient for normal use cases

## Edge Cases Handled

### 1. Hierarchy Endpoint Fails
- **Behavior**: Falls back to `_loadSingleMVRPerson()`
- **Result**: Displays at least direct individuals
- **Log**: `⚠️ Hierarchy not found, falling back to direct MVR load`

### 2. Standalone MVR (Not Merged)
- **Behavior**: `merged_mvr_people` is empty list
- **Result**: `isSuperIndividual = false`, shows as standalone
- **Appearance Count**: Only direct individuals (correct behavior)

### 3. Date Range Filtering
- **Behavior**: Filters individuals by first_seen_timestamp and last_seen_timestamp
- **Result**: Only appearances within date range shown
- **Use Case**: User searches for "individuals seen between 10am-12pm"

### 4. Empty Hierarchy Response
- **Behavior**: Returns null from hierarchy endpoint
- **Result**: Falls back to direct MVR loading
- **Log**: `❌ Could not find person objects data`

## Performance Considerations

### API Call Optimization
- **Single Hierarchy Call**: One call per super-individual (not per individual)
- **Caching**: Routes data cached after first fetch
- **Concurrent Prevention**: `_isLoadingRoutes` flag prevents duplicate requests

### Memory Management
- **Lazy Loading**: Routes not loaded until needed
- **Filtered Data**: Only relevant individuals loaded based on date range
- **Efficient Parsing**: Reuses existing model factories

### Response Time
- **Before**: 1 API call per MVR (15 calls for 15 MVR)
- **After**: 1 hierarchy call gets all data (1 call total)
- **Improvement**: 93% reduction in API calls for merged super-individuals
